## 상세 정리

### 1. 개념

- MSA(Microservices Architecture)는 소프트웨어 개발에서 애플리케이션을 작은 독립적인 서비스로 나누어 개발하는 아키텍처 스타일
- 각 서비스는 특정 비즈니스 기능을 담당하며, 서로 독립적으로 배포되고 확장 가능
- MSA는 모놀리식 아키텍처와 달리, 각 서비스가 독립적으로 개발되고 운영되기 때문에 유연성과 확장성이 높음

### 2. 특징

- Database per Service : 각 서비스는 전용 DB를 가짐
- Polyglot Persistence : 각 서비스는 자신의 도메인에 맞는 최적의 저장소를 선택해서 사용 가능
- Decentralized Governance : 데이터 관리 및 기술 선택의 권한이 각 서비스 팀에 분산
- Infrastructure Automation : 각 서비스는 독립적으로 배포되고 확장 가능

### 3. 장점

- 각 도메인의 비즈니스 특정에 맞는 최적의 저장소를 선택해서 사용 가능
  - 정형 데이터의 경우 관계형 데이터베이스를, 비정형 데이터의 경우 NoSQL 데이터베이스를 사용할 수 있음
- 각 도메인에 따라서 트래픽이 다르다. -> 이를 고려해서 서버를 효율적으로 확장 가능
- 서비스간 장애 전파 방지 가능
- 팀마다 독립적으로 배포 및 개발 가능
- 회사의 비즈니스 방향성 변경에 유연하게 대응 가능

### 4. 단점

- 데이터 일관성 유지가 어려움
  - 분산 트랜잭션 처리가 어려워 최종 일관성을 수용해야함
- 여러 서비스의 통합 테스트가 어려움
- 서비스간 통신이 발생하기 때문에 공수가 더 많이 듬.
- 서비스간 이벤트 발행 내역을 추적하기 어려움.
- 서비스간 발행한 이벤트 유실 가능성을 고려해야함. (Kafka와 같이 이벤트 유실 방지 기능이 있는 메시징 시스템을 사용하거나, 이벤트 발행 시 이벤트 유실 방지 로직을 구현해야함)
- 서비스간 통신이 발생하기 때문에 네트워크 지연이 발생할 수 있음

### 5. 실무에서 볼 포인트

- 언제 MSA를 도입하는 것이 좋을까?
  - 트래픽 관점
    - 트래픽이 증가해 DB가 병목이 될 경우 -> Read Replication만으로는 Write 부하를 감당하기 어려울 때
    - 특정 도메인에 트래픽이 집중되는 경우 -> 특정 도메인에 트래픽이 집중되어 해당 도메인만 확장할 필요가 있을 때
    - 특정 도메인에 트패픽이 집중되어 DB 커넥션을 다 써버리는 경우 -> 다른 기능에도 영향이 감.
  - 도메인 관점
    - 개발 인원이 늘어나서 도메인별로 개발팀이 나뉘어지는 경우 -> 도메인별로 개발팀이 나뉘어져서 각 팀이 독립적으로 개발 및 배포할 필요가 있을 때
    


### 내 생각 정리

상담사나 내담자 정보 뭐 자격증 정보, 상담 증상, 특징 같은 것들이 정규화가 힘듬, 비정형 데이터로 하면 좋겠다는 생각이 듬. (MongoDb 같은 NoSQL 데이터베이스로 관리하는 것이 좋을 것 같음.)
예약 정보는 정합성이 중요하기 때문에 관계형 데이터베이스로 관리하는 것이 좋을 것 같음.

그런데 현실은 서비스 화면 하나 보여주려고 API 여러 개 호출하고 서버에서 데이터 합치고 공수가 너무 많이 듬.
그렇다고 예약 모듈에서 부하가 많은가? 그것도 아님.

관계형 데이터베이스 사용하고 비정형 데이터는 JSON으로 저장하는 게 좋은 선택이지 않을까?
나중에 트래픽이 증가해서 DB가 병목이 될 때, 서버를 분리하는 것을 고려해보는 것도 좋을 것 같음.
