## 상세 정리

### 1. 개념

- 2PC 패턴
  - 분산 트랜잭션을 관리하는 패턴
  - 모든 서비스가 트랜잭션 준비 상태가 될 때까지 대기하고, 모든 서비스가 준비 상태가 되면 commit을 수행하는 방식
- SAGA 패턴
  - 분산 트랜잭션을 관리하는 패턴
    - 각 서비스가 자신의 로컬 트랜잭션을 수행
    - 실패 시 보상 트랜잭션을 실행하여 일관성을 유지하는 방식

### 2. 특징

- SAGA 패턴
  - 확장성 : 각 서비스가 독립적으로 존재하기 때문에 독립적으로 확장 가능. 처리량도 극대화 가능
  - 가용성 : 각 서비스가 독립적으로 존재하기 때문에 특정 서비스에 장애가 발생해도 정상적으로 동작 가능
  - 복잡성 : 각 로컬 트랜잭션마다 보상 트래잭션을 고려해야해서 모든 시나리오를 고려해야함. 유지보수 어려움. 모니터링이 어려움.

- SAGA 패턴 사용 검토
  - MSA 환경인가?
  - 장시간 워크플로우 인가? (예시 : 예약 시스템에서 예약 생성 -> 결제 -> 예약 확정과 같이 여러 단계로 이루어진 워크플로우)
  - 일시적인 불일치를 허용할 수 있는가? (예시 : 상품 재고 감소 -> 결제 승인과 같이 일시적으로 재고 감소와 결제 승인 사이에 불일치가 발생할 수 있는 시나리오)
  - 즉각적인 일관성이 필수인가? (예시 : 계좌 이체)
  - 격리성이 필수인가? (예시 : 주식 거래)

- SAGA 패턴 - Choreography
    각 서비스가 독립적으로 이벤트를 발행하고 구독하는 방식

  - 장점 
    - 느슨한 결합, 즉 서비스는 다른 서비스가 어디에 있는 지 뭘 하는 지 알 필요가 없음.
    - Message Queue를 활용하여 서비스 간의 통신을 비동기적으로 처리
    - 서비스 간의 의존성이 낮아지고 확장성이 높음
  - 단점
    - 서비스간의 이벤트 추적이 어렵다.
      - 서비스에 상태 정보가 분산되어 있기 때문에 장애 발생 시 문제를 진단하기 어려울 수 있다.
    - 복잡성이 변경을 어렵게 한다. 새로운 서비스가 추가될 때 기존 서비스의 이벤트를 구독하도록 변경해야할 수 있다.
    - 순환 의존성 문제가 발생할 수 있다.

- SAGA 패턴 - Orchestration
  중앙에서 트랜잭션의 흐름을 제어하는 오케스트레이터가 존재하는 방식으로 오케스트레이터가 각 명령의 상태를 기록함.(성공 시, 실패 시 ...)

    - 장점
      - 트랜잭션 흐름이 중앙에서 제어되기 때문에 장애 발생 시 문제를 진단하기 쉬움 (오케스트레이터에 상태 관리)
      - 동기적, 순차적이기 때문에 추적 가능성이 좋다 (단순히 로그를 통해서 디버깅 가능)
    - 단점
      - 오케스트레이터가 SPOF (Single Point Of Failure)가 될 수 있음
        - 여러 서비스와 통신해야하기 때문에 오케스트레이터가 장애가 발생할 경우 전체 트랜잭션이 실패할 수 있음
      - 오케스트레이터에 대한 의존성이 높아짐
        - API Spec 수정, 이벤트 추가 등

## 남은 질문

- '상담 예약 -> 상담 확정 -> 상담 완료' 이 워크 플로우에서 크레딧 차감 시점을 어디에 두어야할까?
  - 크레딧 선차감 후 상담 취소되면 크레딧 환불 
    - 장점
      - 상담 예약or확정 시점에 크레딧이 차감되기 때문에 상담 확정 시점과 상담 완료 시점에서 크레딧 차감 여부를 고려할 필요가 없음.
    - 단점
      - 상담 예약or확정 시점에 크레딧이 차감되기 때문에 상담 예약이 취소될 경우 크레딧 환불 로직이 필요함.

  - 크레딧 잠금 후 상담이 완료가 되면 크레딧 차감 
    - 장점 : 크레딧이 잠가지기 때문에 크레딧이 없는 상황에 상담 예약이 되는 것을 방지할 수 있음.
    - 단점 : 상담 취소 or 상담 완료 시 크레딧 복구 및 차감 로직이 필요함.
